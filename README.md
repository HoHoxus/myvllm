# myvllm

A personal learning project built on top of
[nano-vllm](https://github.com/GeeeekExplorer/nano-vllm).

The goal is to understand and re-implement core LLM inference components
(kernels, attention mechanisms, and inference internals) from scratch while
keeping the codebase small and readable.

## Roadmap

Status: ✅ Partial implementation and testing completed; 🚧 Code base exists, pending completion or verification; ⬜ Not yet implemented.
🚧 does not mean end-to-end inference verification has passed; multi-GPU projects require corresponding hardware.

### Attention and Execution Optimization

- 🚧 **FlashAttention (Triton)** · vLLM / SGLang · Medium: Reduce memory reads and writes of intermediate attention matrices through tiled computation and online softmax. A prefill kernel already exists, but the calling parameters of `Attention.forward` are inconsistent with the function signature; first fix the interface, then align numerical results with PyTorch attention. [vLLM Technical Overview](https://github.com/vllm-project/vllm#about)
- 🚧 **PagedAttention / Paged KV Cache** · vLLM / SGLang paged attention backend · Medium: Manage non-contiguous caches using a logical page to physical KV block mapping, reducing the constraints of contiguous memory allocation. A `BlockManager` and a draft decode kernel already exist, but there are typos in the kernel, and the decode branch has not yet been connected; single-step decode correctness verification should be completed first. [vLLM Technical Overview](https://github.com/vllm-project/vllm#about)
- 🚧 **CUDA Graph Replay** · vLLM / SGLang · Medium: Capture and replay GPU execution graphs to reduce CPU launch overhead during per-token decoding. `model_runner.py` already has logic for capturing and replaying by batch size; after the inference pipeline is fixed, verify consistency among padding, dynamic lengths, and eager mode. [vLLM Technical Overview](https://github.com/vllm-project/vllm#about)
- ⬜ **Operator Fusion and torch.compile Optimization** · vLLM / SGLang · Medium: Reduce the number of small operator launches and intermediate tensor reads/writes. Some existing operators already use compiled or fused implementations; starting from profiling, further attempts can be made to fuse residual + RMSNorm, activation and multiplication; keep the unfused implementation as a numerical baseline. [vLLM Technical Overview](https://github.com/vllm-project/vllm#about)

### Scheduling and KV Cache Reuse

- 🚧 **Continuous Batching** · vLLM / SGLang · Medium: Reorganize requests each round, promptly remove finished requests, and allow new requests without waiting for the entire batch to complete. `scheduler.py` already has waiting/running queues; experiments with dynamically arriving requests can be added to check admission, preemption, and recycling behavior. [vLLM Technical Overview](https://github.com/vllm-project/vllm#about)
- 🚧 **Chunked Prefill and Mixed Scheduling** · vLLM / SGLang · Medium: Split long prompts into multiple token chunks to avoid a single prefill occupying the GPU for a long time. Token budgets and chunk counts already exist, but prefill is currently prioritized; the next step can be to let decode and prefill chunks execute in the same round, comparing first-token latency and inter-token latency. [vLLM Scheduling Optimization](https://docs.vllm.ai/en/latest/configuration/optimization/), [SGLang Scheduling Parameters](https://docs.sglang.io/docs/advanced_features/server_arguments#memory-and-scheduling)
- 🚧 **Automatic Prefix Caching** · vLLM / SGLang · Medium: Share KV for identical token prefixes, reducing repeated prefill for common system prompts and multi-turn conversations. `block_manager.py` already has chained hashing, reference counting, and full-block reuse; it is necessary to first complete prefill attention that can read cached prefixes, then verify output consistency between cache hits and misses. [vLLM Technical Overview](https://github.com/vllm-project/vllm#about)
- ⬜ **RadixAttention / Radix Cache** · SGLang · Medium-High: Organize reusable token prefixes using a compressed prefix tree. Starting from the existing hash cache, a radix tree can be added to compare matching overhead, sharing granularity, and cache hit rate; this is another implementation route for prefix caching. [SGLang Radix Cache](https://docs.sglang.io/docs/advanced_features/radix_eviction_policy)
- ⬜ **Cache Eviction Policies (LRU / LFU, etc.)** · SGLang · Simple to Medium: When KV space is insufficient, preferentially evict caches that are no longer referenced by requests and have lower reuse value. Access time or frequency can be recorded in `BlockManager` to compare hit rates and recomputed token counts under different policies. [SGLang Eviction Policies](https://docs.sglang.io/docs/advanced_features/radix_eviction_policy)
- ⬜ **Overlap Scheduling (CPU/GPU Overlapped Scheduling)** · SGLang · Relatively Hard: While the GPU executes the current batch, let the CPU prepare the next round of scheduling and inputs, reducing mutual waiting between the two. `LLMEngine.step` and `ModelRunner` can be extended using asynchronous results and double buffering; dependencies of the next round's tokens on the current results need to be handled. [SGLang Runtime Parameters](https://docs.sglang.io/docs/advanced_features/server_arguments)

### Sampling and Decoding

- ✅ **Greedy Decoding** · vLLM / SGLang · Simple: When `temperature=0`, select the token corresponding to the maximum logit; mixed batching with random sampling is already supported, and CPU unit tests have been completed. Full model inference still awaits GPU verification. [SGLang Sampling Parameters](https://docs.sglang.io/docs/basic_usage/sampling_params)
- ⬜ **Top-k / Top-p and Repetition Penalty** · vLLM / SGLang · Simple: Limit the sampling candidate range, or adjust logits based on historical tokens. `SamplingParams`, `Sequence`, and `Sampler` can be extended; implement the PyTorch version first, then consider fused kernels. [SGLang Sampling Parameters](https://docs.sglang.io/docs/basic_usage/sampling_params)
- ⬜ **Structured / Constrained Decoding** · vLLM / SGLang · Medium: Mask illegal tokens according to grammar state so that outputs satisfy constraints such as regular expressions and JSON Schema. It can start with finite options or a simple state machine, applying a logits mask before sampling, and later integrating a grammar backend. [SGLang Structured Outputs](https://docs.sglang.io/docs/advanced_features/structured_outputs)
- ⬜ **N-gram Speculative Decoding (Draft-Model-Free Speculative Decoding)** · vLLM / SGLang · Medium-High: Propose multiple candidates from repeated segments in existing tokens, then batch-verify them with the target model. No additional model weights are required, making it suitable as a starting point for speculative decoding; multi-token verification, KV rollback after rejection, and greedy result consistency need to be ensured first. [SGLang Speculative Decoding](https://docs.sglang.io/docs/advanced_features/speculative_decoding)
- ⬜ **Draft-model Speculative Decoding** · vLLM / SGLang · Relatively Hard: Use a smaller model to propose multiple tokens, then verify them with the target model, reducing the number of serial rounds executing the target model. A single-request dual-model prototype with the same tokenizer can be built first; the random sampling version needs to implement the correct acceptance probability and rejection resampling, and cannot directly reuse greedy verification. [SGLang Speculative Decoding](https://docs.sglang.io/docs/advanced_features/speculative_decoding)

### Quantization and Multi-GPU Scaling

- ⬜ **Weight Quantization (INT8 / INT4, AWQ / GPTQ, etc.)** · vLLM / SGLang · Medium-High: Use low-bit-width weights to reduce model memory usage and weight read bandwidth. A quantized linear layer can first be added to `layers/linear.py`, then weight loading can be extended; real speedup depends on the corresponding low-precision GEMM, and simply dequantizing before calling ordinary matrix multiplication may not be faster. [SGLang Quantization Parameters](https://docs.sglang.io/docs/advanced_features/server_arguments#quantization-and-data-type)
- ⬜ **KV Cache Quantization** · vLLM / SGLang · Medium-High: Store KV in formats such as FP8 to reduce cache memory requirements for long contexts and high concurrency. Cache allocation, scale management, writes, and attention reads need to be modified together, and accuracy loss must be measured; hardware and backend support will affect the benefits. [SGLang KV Quantization](https://docs.sglang.io/docs/advanced_features/quantized_kv_cache)
- 🚧 **Tensor Parallelism** · vLLM / SGLang · Medium-High: Split the weights and computation of the same layer across multiple GPUs, with communication to complete the forward pass. Sharded linear layers, distributed communication, and a multi-process entry point already exist; multi-GPU verification of loading, KV head sharding, and output correctness is needed. [vLLM Parallelism Strategies](https://docs.vllm.ai/en/latest/configuration/optimization/#parallelism-strategies)
- ⬜ **Data Parallelism** · vLLM / SGLang · Medium: Multiple independent model replicas process different requests, improving overall throughput. A request dispatcher can be added outside the existing engine, with each replica managing KV independently; implement round-robin or queue-length-based dispatch first. [vLLM Parallelism Strategies](https://docs.vllm.ai/en/latest/configuration/optimization/#parallelism-strategies)
- ⬜ **Prefill-Decode Disaggregation (PD Disaggregation)** · vLLM / SGLang · Relatively Hard: Different workers execute prefill and decode, connecting the two stages through KV transfer so that resources can be allocated separately. A single-machine dual-GPU prototype can be built first; KV export/import, block mapping, and request handoff protocols need to be defined, and transfer costs evaluated. [SGLang PD Disaggregation](https://github.com/sgl-project/sglang/blob/main/docs/docs/advanced_features/pd_disaggregation.mdx)

Suggested order of advancement: fix and verify the main attention pipeline → Top-k / Top-p → cache eviction policies →
verify prefix caching and chunked prefill → mixed scheduling and CUDA Graph → N-gram speculative decoding → quantization or multi-GPU experiments.
EAGLE / MTP, MoE expert parallelism, and others depend on specialized weights or new model structures, and are not included in the direct implementation list of the current minimal framework for now.
